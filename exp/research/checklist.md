# 候选“肩膀高度”检查标准

[返回线索白板](../README.md)

## 研究问题

一个上游项目能否真正减少 Web TUI Engine 的未知、实现量和长期维护，而不引入第二套系统权威？

## 高度评级

| 等级 | 含义 |
| --- | --- |
| A | 提供成熟稳定的直接能力，或补齐多个关键架构契约与高价值测试资产 |
| B | 提供一个重要子系统蓝图或完整行为矩阵，但不能直接成为核心依赖 |
| C | 只有局部算法、fixture 或产品案例值得参考 |
| D | 与目标冲突、重复现有能力，或采用成本高于收益 |

肩膀高度与采用状态独立。例如 Flutter 的架构高度为 A，但直接依赖高度为 D。

## 采用状态

| 状态 | 含义 |
| --- | --- |
| `依赖候选` | 存在稳定公共边界，但尚未通过本地采用门槛 |
| `分层采用` | 只采用明确的 package 或能力，不采用完整运行时 |
| `观察上游` | 能力匹配，但目标平台的官方交付边界尚未成熟 |
| `条件后备` | 仅在卡片所列触发条件成立时评估或采用 |
| `可直接复用` | 现有稳定公共边界可作为依赖消费 |
| `仅作蓝图` | 只消费架构、行为或测试契约，不引入运行时依赖 |
| `不采用` | 已确认与产品约束或系统权威冲突 |

## 必查项

1. 项目形态、维护状态、许可证、发布与版本边界。
2. 相对现有线索新增了什么，是否只是重复同类结论。
3. 哪些 public package/API 可直接消费，哪些只能参考源码或 tests。
4. 是否建立第二套 layout、paint、scroll、event、focus、selection 或 semantics 权威。
5. Browser、DOM、px、WASM、React 与平台 runtime 的耦合位置。
6. Input、IME、clipboard、touch、accessibility 与国际化的真实覆盖。
7. 大数据虚拟化、dirty rendering、增量更新与性能证据。
8. 官方 tests、fixtures、benchmarks、debugging 工具能否作为 behavior oracle。
9. 最小 Spike、可观测指标、采用阈值与硬淘汰条件。
10. 能减少哪些初始手搓和长期维护，又会新增哪些依赖成本。

## 输出要求

- 事实只引用官方文档、仓库、源码、tests、issues 或 releases。
- 分别给出架构/产品高度与直接依赖高度。
- 明确标记直接依赖、封装后依赖、隔离 Foreign Surface、仅作蓝图或不采用。
- 量化估算必须标记为工程估算，不伪装成上游数据。
- 上游内部路径不是稳定 API；deep import 必须判为维护 fork。
- 如果采用要求复制本项目已有的 Widget Tree、SceneGeometry、CellBuffer 或 SemanticSnapshot，默认淘汰。
